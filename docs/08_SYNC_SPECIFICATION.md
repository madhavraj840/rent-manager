## 1. Principles

1. **The server is the only source of truth.** The phone holds a cache plus a queue of the user's intentions.
2. **Every change is an operation (op) with a unique `op_id`,** applied at most once.
3. **Every record has a client- or server-generated UUID,** so retries can never create a second record.
4. **Money is append-only.** Payments, charges, credits and refunds are never merged or overwritten, only voided. Two offline payments are two payments.
5. **Ordering comes from the server,** through a per-workspace version number. Device clocks are never used to decide anything.
6. **Rule violations are rejected, never auto-fixed.** The user sees exactly what failed and chooses what to do.
7. **The website is online-only.** It reads and writes the server directly, so only the Android app runs this protocol (D-019).

These call REST directly and show "Connect to the internet to …" when offline.

## 3. Server source of truth

- Every write, from the website, a push op or a job, goes through a command (06 §6). The command locks the workspace counter, stamps `version`, checks invariants and writes an audit event.
- The server returns the **canonical record** after each write. Clients always replace their local copy with it.
- Server-owned fields that clients never set: `version`, `created_at`, `updated_at`, `created_by`, `updated_by`, `receipt_number`, `possible_duplicate_of`, the `voided_*` fields (timestamp/user), and all charges generated by jobs.

## 5. Record versions and timestamps

### 5.1 Why versions, not timestamps
Clocks on phones are wrong or changed by users, and even server timestamps from concurrent transactions commit out of order. A client that pulls "changes since 10:42:00" can miss a row written at 10:41:59 by a transaction that committed after 10:42:00. The design therefore uses a **per-workspace integer version** assigned in commit order.

### 5.2 How versions are assigned
Every write transaction first runs:
```sql
UPDATE app.workspace_counters SET change_seq = change_seq + 1
 WHERE workspace_id = $ws RETURNING change_seq;   -- takes a row lock until COMMIT
```
The trigger `app.stamp_version()` sets `version` = that number on every row written in the transaction. Because the row lock is held until commit, a later transaction in the same workspace can only get a higher number **after** the earlier one committed. Versions are therefore visible in commit order, and a cursor never skips a row.

Cost: writes in one workspace are serialized. At the expected load (< 1 write/second per workspace, peaks on the 1st of the month) this is acceptable. Different workspaces never block each other.

### 5.3 Timestamps
- `created_at` / `updated_at` are server times for display and audit only.
- Business dates (`entry_date`, `due_date`, `reading_date`, `moved_out_on`…) are dates the user enters. They are validated by the server against its own "today" in the workspace time zone (BR-021).
- Device time is used only to show "recorded 5 min ago" for pending items.

## 6. Offline transactions (local write path)

### 6.1 Write path
Every user action on Android runs in **one Room transaction**:

1. Validate with the shared domain validators (the same rules as the server's Zod schemas).
2. Write the new or changed local rows with `local_status = PENDING` (optimistic UI).
3. Insert the op into `pending_ops` with `depends_on` filled from the pending creates it references.
4. Commit, then schedule the `sync` work (debounced 2 s, network required).

The UI observes Room, so balances, statuses and lists update immediately, and the local money engine includes pending entries.

### 6.2 Atomic compound operations
Some actions must succeed or fail as a whole, locally and on the server:

| Op type | Contains | Why atomic |
|---|---|---|
| `tenancy.start` | tenancy, parties, first revision, recurring charges, initial entries (with generated keys), opening entries, readings, inspection + items | No half-created tenancy; prevents the job from generating a charge in between |
| `tenancy.move_out` | move-out date, readings, move-out inspection, settlement draft | Consistent settlement input |
| `settlement.finalize` | all settlement lines + expected totals | Money close-out must be exact (§11.5) |
| `tenancy.revise_rent` | revision + adjustment entries | |
| `reading.create` | reading(s) (incl. replacement pair) + optional utility charge | Charge must match readings |
| `unit.bulk_create` | up to 200 units | All-or-nothing label check |

### 6.3 Op catalogue (offline-capable)
Each type maps to exactly one REST command (07). Payload = that endpoint's body.

| Area | Op types |

### 6.4 Undo before sending
If the user voids or deletes something whose **create op is still PENDING and not in flight**, the create op and all ops depending on it are removed, and the local rows are deleted. Nothing reaches the server and nothing appears in the audit log (F-PAY-2 edge case). Once the op has been sent (IN_FLIGHT or applied), a normal void/delete op is queued instead.

## 7. Upload queue (push)

### 7.1 Request
`POST /api/v1/workspaces/{ws}/sync/push`
```json
{
  "device_id": "b1f0…",
  "client_version": 12,
  "ops": [
    { "op_id": "0c9e…", "schema": 1, "type": "ledger.payment", "entity_id": "c4a2…",
      "data": { "tenancy_id": "7d1e…", "account": "RENT", "amount_minor": 1500000,
                "entry_date": "2026-10-03", "method": "CASH", "reference": null, "note": null } }
  ]
}
```
- Ops are sent in `seq` order, up to 100 per request (server limit 500 / 5 MB).
- Only ops with `user_id` = current session user and status PENDING are sent. BLOCKED ops (their dependency FAILED) wait.

### 7.2 Server processing
For each op, in order, the server:

1. Looks up `op_id` in `sync_ops`. If found, it returns the stored result (**DUPLICATE**) without re-applying.
2. Checks authorization for this op (role and property scope, 01 §12).
3. Validates the payload (same Zod schema as the REST endpoint).
4. Runs the command in its own transaction: workspace lock → invariants → writes → audit (with `op_id`, source ANDROID).
5. Stores `{op_id, status, result}` in `sync_ops` in the same transaction as the writes, so "applied" and "recorded" cannot diverge.
6. Adds the result to the response.

If an op fails, later ops **in the same batch** that reference an entity the failed op should have created get `DEPENDENCY_FAILED`. Unrelated ops continue.

The server stops after ~20 s and returns partial results with `"remaining": true`; the client sends the rest in the next request.

### 7.3 Response
```json
{
  "results": [
    { "op_id": "0c9e…", "status": "APPLIED",
      "entities": [{ "type": "ledger_entries", "row": { "id": "c4a2…", "version": 18431, "receipt_number": "R-000123", "…": "…" } }],
      "warnings": [] }
  ],
  "remaining": false,
  "min_client_version": 12
}
```

| Result status | Meaning | Client action |
|---|---|---|
| APPLIED | Done | Replace local rows with `entities`; delete op; `local_status` SYNCED (unless other ops pending on the row) |
| DUPLICATE | Already applied earlier (response had been lost) | Same as APPLIED using the stored result |
| REJECTED | Rule or validation failure (`error.code`, `error.message`, `error.details`) | Op → FAILED; rows → FAILED; dependents → BLOCKED; appears in Sync issues |
| CONFLICT_DELETED | Target entity was deleted on the server | Drop op; delete local row; info entry "Deleted on another device" |
| FORBIDDEN | Role/scope does not allow it (anymore) | Op → FAILED (issue with "You no longer have access") |
| DEPENDENCY_FAILED | An earlier op in this batch that this op needs failed | Op → BLOCKED |
| RETRY_LATER | Transient server problem for this op | Keep PENDING; retry with backoff |

Whole-request errors: `401` → token refresh then retry (§14); `426 CLIENT_TOO_OLD` → stop, require update; `403` on the workspace → access flow (§15); network error, `5xx`, `429` → retry with backoff (§13).

## 8. Idempotency and duplicate prevention

| Risk | Protection |
|---|---|
| Same op sent twice (retry after timeout) | `op_id` lookup in `sync_ops` → DUPLICATE with the original result |
| Same create re-sent after `sync_ops` expired (> 90 days offline) | Entity `id` already exists with identical payload → treated as applied (ID-based idempotency, 07 §1.7) |
| Same id, different payload (bug) | `409 ID_CONFLICT` → REJECTED, visible as a sync issue |
| Double tap in the UI | Buttons disabled while saving; one op per save |
| Same real-world payment entered on two devices | Cannot be prevented technically (different ids). Server flags the later one with `possible_duplicate_of` (same tenancy, amount, date, within 24 h); both clients show "Possible duplicate" until a person voids one or dismisses the flag |
| Job generating the same rent twice | `generated_key` unique (05 §2.15) |
| Void sent twice | Voiding a VOID entry is a no-op success |

## 9. Download changes (pull)

### 9.1 Request / response
`GET /api/v1/workspaces/{ws}/sync/pull?cursor=18400&limit=1000`
```json
{
  "cursor": 18431,
  "has_more": false,
  "changes": {
    "ledger_entries": [ { "id": "…", "version": 18431, "deleted_at": null, "…": "…" } ],
    "tenancies": [ … ],
    "documents": [ { "id": "…", "version": 18420, "deleted_at": "2026-10-03T09:00:00Z" } ]
  },
  "min_client_version": 12,
  "server_time": "2026-10-03T10:42:07Z"
}
```

### 9.2 Server algorithm (no split versions)
1. For each synced table, select rows in scope with `version > cursor`, ordered by version, `LIMIT limit`.
2. Merge-sort the candidates and take the first `limit` rows. Let `V` be the version of the last row taken.
3. If more rows exist with version exactly `V` (in any table), include them too. All rows of one transaction share one version, so a page never contains half a transaction.
4. Return `cursor = V` and `has_more`.

Tombstones (`deleted_at` set) are included like any other change. Rows the caller cannot see are filtered by the scope rules in §2.

### 9.3 Client apply (one Room transaction per page)
For each row R:
1. **Tombstone:** delete the local row. Pending ops targeting it are removed and logged as "Deleted on another device" (delete wins, §16).
2. **Entity has pending ops:** store R as the base, then **re-apply** each pending op's changes on top, in `seq` order (rebase). The row stays PENDING. This keeps the user's unsent edits visible and matches what the server will produce when they arrive (their fields arrive later, so they win under D-020).
3. **Otherwise:** upsert R, `local_status = SYNCED`.

Then save `cursor = response.cursor` in the same transaction. If the app dies mid-page, nothing from that page is applied and the page is fetched again.

### 9.4 Triggers
Pull runs after every successful push, on app foreground, on pull-to-refresh, every 15 minutes while online (WorkManager periodic), and after the network returns. In V1, a silent FCM "data changed" message also triggers a pull (SYNC-010).

## 10. Initial sync

| Step | Behaviour |
|---|---|
| When | After sign-in, when opening a workspace for the first time on this device, after an access change (§15), or after `RESYNC_REQUIRED` |
| How | Pull from `cursor = 0` page by page (limit 2,000), saving the cursor after each page |
| UI | Full-screen "Preparing your data… 45%". Writes are disabled until complete, so validations have the data they need. |
| Interrupted | Resumes from the saved cursor next time |
| Size | 500-unit workspace ≈ 100k rows ≈ 30 MB JSON (≈ 5 MB gzipped) → target < 60 s on 4G (NFR-002) |
| Files | Not downloaded; opened on demand and cached (§12) |

`RESYNC_REQUIRED` (409) is returned when the client's cursor is older than the workspace's `purge_floor`, meaning tombstones that client never received were purged (§16.3).

## 11. Conflict detection and resolution

### 11.1 Rules by data type

| Data | Detection | Resolution | Owner's answer (Q16) satisfied by |
|---|---|---|---|
| Normal fields (names, phones, notes, settings, terms such as lease end) | Not detected as conflicts | **Field-level last-write-wins by server arrival order.** Updates carry only changed fields. Different fields edited on two devices both survive. For the same field, the later arrival wins; the earlier value stays in the audit log. | "One of them will be taken into account" |
| Money entries (ledger) | Immutable; only annotate/void | Two creates = two entries (possible-duplicate flag). Void twice = no-op. Void of an entry inside a finalized settlement = REJECTED. | Money is never lost |
| Unique/overlap rules (tenancy overlap, unit label, rent revision date, meter reading date, one open settlement) | Database constraint on the second write | Second write REJECTED with the conflicting record in `details` | Explicit, user resolves |
| Balance invariants (deposit held ≥ 0, refund ≤ credit, apply ≤ balance) | Command checks against current server state | The op that would break the rule is REJECTED | Explicit |
| Tenancy state (CLOSED/CANCELLED) | Command checks | Money ops REJECTED (TENANCY_CLOSED) | Explicit |
| Delete vs edit | Target has `deleted_at` | Delete wins: edits get CONFLICT_DELETED and are dropped with a notice | — |
| Settlement finalize vs other ledger changes | Server recomputes totals vs `expected` | SETTLEMENT_STALE → client shows the new preview for reconfirmation | Explicit |
| Server-generated charges | Only the server creates them | No conflict possible | — |

### 11.2 Why arrival order and field level
Arrival order needs no trustworthy clock. Field level avoids losing unrelated edits, which record-level LWW would cause (e.g. phone edits the tenant's email, web edits the phone number). The trade-off: a phone that was offline for days can overwrite a newer web edit of the **same field**. The audit log shows both values, and Owner/Admin can restore the old one. (PROVISIONAL D-020. The alternative would be rejecting stale edits, which needs per-field versions and a merge UI.)

### 11.3 Sync issues: what the user sees and can do
| Code | Plain message | Actions |
|---|---|---|
| UNIT_OCCUPIED | "Room 101 already has a tenancy for these dates (Rahul, from 1 Sep)." | Edit dates/unit · Discard (and N dependent changes) |
| TENANCY_CLOSED | "This tenancy was closed on 14 Mar. Your payment of ₹5,000 wasn't saved." | Ask Owner/Admin to reopen settlement · Discard · Copy details |
| DEPOSIT_INSUFFICIENT / REFUND_EXCEEDS_CREDIT | "Only ₹10,000 is available to refund now." | Edit amount · Discard |
| READING_DUPLICATE | "A reading for this meter on 18 Oct already exists (4,951.5)." | Change date · Discard |
| DUPLICATE_NAME | "A property named 'Green Villa' already exists." | Rename · Discard |
| FORBIDDEN | "You no longer have access to this property." | Discard · Copy details |
| SETTLEMENT_STALE | "Balances changed since you prepared this settlement." | Review new settlement |
| VALIDATION_FAILED | Field messages | Edit · Discard |

"Edit" opens the original form prefilled with the op payload. Saving replaces the failed op with a **new op** (new op_id) at the same position and unblocks its dependents. "Discard" asks for confirmation, then reverts local rows (creates are deleted; updates are refetched with `GET /sync/entities`) and discards dependents after listing them.

## 12. Files

1. The user attaches a photo or PDF. The app compresses images, copies the file to `filesDir/docs/<document_id>`, writes the document row + `document.create` op + `local_files` row (PENDING_UPLOAD).
2. The `upload-files` worker (network required) waits until `document.create` is APPLIED, then: request upload URL → PUT file → `complete` → state UPLOADED.
3. Failure → backoff retries; after 10 failures it appears in Sync issues ("Photo couldn't upload") with Retry/Remove.
4. Viewing: local file if present; otherwise download URL → cache (CACHED). Sensitive documents are cached only in `cacheDir` and cleared on sign-out (11 §7).
5. `document.delete` of a never-uploaded document removes the local file and the pending op (§6.4).

## 13. Retry logic and network failure

| Situation | Behaviour |
|---|---|
| No network | Work waits for the connectivity constraint; UI shows "Offline · N changes waiting" |
| Timeout / connection reset / 5xx / 429 | WorkManager exponential backoff: 30 s, 60 s, 2 min … capped at 1 h (429 honours `Retry-After`) |
| Op RETRY_LATER | Stays PENDING; retried in the next run |
| Op REJECTED/FORBIDDEN | No automatic retry; needs user action |
| Op PENDING > 24 h | Daily local notification (NOTIF-005) |
| App killed during push | Ops remain PENDING/IN_FLIGHT; IN_FLIGHT ops are reset to PENDING on next start and re-sent (idempotent) |
| Partial batch processed | Results for processed ops applied; the rest re-sent |
| Mid-page pull failure | Page not applied; refetched |

## 14. Authentication expiry, user switching, app versions

- **Access token expired:** the OkHttp authenticator refreshes it with the refresh token and repeats the request once.
- **Refresh fails** (signed out elsewhere, session revoked): sync state AUTH_REQUIRED, banner "Sign in again to sync 12 changes". Pending ops stay on the device.
  - Same user signs in → sync resumes.
  - Different user signs in → their data syncs separately. The previous user's ops are **never** sent under the new identity (ops carry `user_id`). The previous user's data can be recovered by signing in as that user again. "Discard their changes" needs explicit confirmation.
- **Sign-out with pending ops:** blocked with "N changes not synced. Sync now / Sign out and discard" (F-ACC-2).
- **App too old:** every response carries `min_client_version`. If the app is older, sync stops and an immediate in-app update is required. Pending ops are kept, because the new app version still understands `schema: 1` ops; the server supports each op schema for ≥ 6 months after a new schema appears.

## 15. Access changes and revocation

- The client recomputes `access_hash` from its own membership rows after each pull.
- **Hash changed** (role or property scope changed): wipe the workspace's mirror tables (keep `pending_ops`), set cursor = 0, run the initial sync, then re-apply pending ops locally (rebase). Ops now outside scope will come back FORBIDDEN.
- **Revoked** (membership REVOKED or `403`/`404` on pull): dialog "Your access to Sharma Properties was removed." If pending ops exist, "Copy unsynced changes" produces a plain-text summary the user can share, so information is not silently lost. Then the workspace's local data, files and ops are wiped.

## 16. Deletes

1. **Soft delete everywhere:** deletes set `deleted_at` (tombstone) and bump the version, so pulls deliver them.
2. **Delete wins** over concurrent edits (§11.1). Deletion is also blocked by dependency rules (HAS_DEPENDENCIES). Records with history are archived, not deleted.
3. **Purge and resync:** tombstones and soft-deleted documents may be purged after 90 days. The purge job records the highest purged version in `workspace_counters.purge_floor`. A client whose cursor is below it receives `409 RESYNC_REQUIRED` and runs a full initial sync, so it cannot keep ghosts of purged rows.
4. **Money entries are never deleted** (void instead). Whole-workspace purge deletes everything and clients receive `404`.

## 17. Concurrent edits: consolidated rules

| Scenario | Result |
|---|---|
| Phone and web edit different fields of one record | Both kept |
| Phone and web edit the same field | Later arrival at server wins; audit shows both |
| Two devices record payments for the same tenancy | Both kept; later one flagged possible duplicate if same amount + date within 24 h |
| Two devices start tenancies on one unit with overlapping dates | First to arrive wins; second REJECTED (UNIT_OCCUPIED) |
| Two devices add rent revisions for the same date | Second REJECTED (REVISION_EXISTS) |
| Device refunds deposit that another device already applied | Second REJECTED (DEPOSIT_INSUFFICIENT) |
| Web finalizes settlement; phone recorded a payment offline | Phone payment arrives: tenancy ENDED → accepted (balance changes; settlement shows updated owed/refund); tenancy CLOSED → REJECTED (TENANCY_CLOSED) |
| Phone finalizes settlement offline; web recorded a payment meanwhile | Finalize REJECTED (SETTLEMENT_STALE); user reviews the new preview |
| Web deletes a tenant; phone edits it offline | Edit dropped (CONFLICT_DELETED) with notice. If the tenant has tenancies, the delete itself was never allowed. |
| Job generates October rent while phone is offline | Phone receives it on next pull; offline payments already recorded apply to it by FIFO |

```mermaid
    Note over P,W: Both payments exist. Balance shows ₹15,000 advance. Both clients show "Possible duplicate".
    W->>S: Owner voids B ("same cash entered twice")
```
If the tenant really paid twice (two months), no one voids and FIFO applies the second payment to the next charge. Nothing is duplicated or lost; a person decides.

### E3 — Same tenant edited on phone and website
- Phone (offline, 10:00): tenant email → `r@x.com`, phone → `+91 98…11`.
- Website (online, 10:30): tenant phone → `+91 98…22`.
- Phone syncs at 11:00: its patch `{email, phone}` arrives after the web edit.
- Result: email = `r@x.com` (only the phone changed it), phone = `+91 98…11` (later arrival). Audit log: 10:30 web set phone …22; 11:00 android set phone …11 (before …22). An Owner can restore it from the audit log.

### E5 — Tenant deleted on the website while the phone edits it offline
The website deletes a prospect tenant with no tenancies (allowed). The phone's `tenant.update` arrives and gets `CONFLICT_DELETED`. The phone drops the op, deletes the local row, and logs "Tenant 'Amit' was deleted on another device" in the sync log (informational, no action needed).

### E6 — Response lost
The phone sends op 0c9e and the server applies it, but the connection drops before the response arrives. The phone retries with the same op 0c9e and the server returns **DUPLICATE** with the stored result. There is exactly one payment and one receipt number.

### E7 — Offline for 3 weeks, token expired, another person uses the phone
The phone has 40 pending ops (user Priya). The refresh token was revoked by "Sign out of all devices", so state = AUTH_REQUIRED. If Priya signs in, the 40 ops are sent. If Ravi signs in instead, his workspace syncs normally, and Priya's 40 ops stay parked with the prompt "40 changes by priya@… are waiting. Ask Priya to sign in, or discard them." They are never sent as Ravi.

### E8 — Settlement finalized on the website; phone payment arrives later
- Finalized with tenant owing ₹2,000 → tenancy ENDED. The phone's offline ₹2,000 payment arrives and is accepted. Both balances are zero, so the tenancy is CLOSED automatically.
- Finalized with refund paid and balances zero → tenancy CLOSED. The phone's payment arrives and is REJECTED (TENANCY_CLOSED). The sync issue suggests "Ask an Owner/Admin to reopen the settlement" or "Discard".

### E9 — Two devices refund the same advance
Advance credit ₹5,000. Phone A refunds ₹5,000 offline, and phone B refunds ₹5,000 offline. A arrives first and is APPLIED. B gets REJECTED with REFUND_EXCEEDS_CREDIT ("Only ₹0 is available to refund now"), and the user discards it.

## 20. Limits and non-goals (MVP)

- No realtime push of changes to phones (V1 adds FCM-triggered pull). Freshness is ≤ 15 minutes while the app is open or backgrounded with network.
- No partial sync: a device holds all in-scope data of a workspace (target ≤ 2,000 units, D-047).
- No CRDTs or automatic merging of money. Humans resolve the rare conflicts.
- The website does not work offline.
